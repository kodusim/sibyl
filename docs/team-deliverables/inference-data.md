# 추론·데이터팀 첫 설계

상태: 설계 초안. 아래 분류·수치·알고리즘 선택은 미검증 가설이며 구현·사용자 평가 결과가 아니다.

## 제품과 범위

질문에 답하면 무당이 찾아온 이유를 짚는 게임을 만든다. 첫 판에서 가장 마음에 걸리는 고민 하나를 떠올리도록 안내하되 내용을 입력하게 하지 않는다. 첫 실험은 일상적 관계 고민을 후보 범위로 제안한다. 범위 확정은 제품팀·대표가 맡는다.

초기 후보 예시: 상대의 호감이 불확실함, 연락을 먼저 할지 망설임, 관계를 끝낼지 고민함, 거절 후 관계가 어색해질까 걱정함. 이는 확정 분류가 아니다. 관계의 종류·감정·결정 과제를 나누어 정의하고 중복 사례를 검토한다.

## 데이터 계약 초안

| 객체 | 필드와 의미 |
| --- | --- |
| Candidate | `id`, `version`, `label`, `domain`, `coreTension`, `includeExamples`, `excludeExamples`, `featureIds` |
| Question | `id`, `version`, `semanticText`, `featureId`, `wordingId`, `eligibility`, `answerLikelihoods`, `sensitivity`, `correlationGroup` |
| Answer | `questionId`, `questionVersion`, `value`: `yes / probably_yes / unknown / probably_no / no` |
| Session | `id`, `dataVersion`, `answers`, `askedIds`, `rejectedCandidateIds`, `status` |
| InferenceResult | `status`, `candidateIds`, `evidenceAnswerIds`, `contradictions`, `uncertaintyReason`, `nextQuestionId` |

`answerLikelihoods`는 후보별 답변 분포 초안이며 실측값이 아니다. 질문별 분포는 합이 1인지 검증하고 0으로 후보를 영구 제거하지 않는다. `unknown`은 증거 없음으로 처리한다. 질문 표현과 의미 버전을 함께 고정한다.

예시 질문의 의미: “지금 가장 궁금한 것은 상대가 나를 어떻게 생각하는지인가?” 결과가 답변을 단순 반복하지 않도록, 하나의 질문에서 결론 전체를 노출하는 문항은 별도 평가한다.

## 엔진과 표현의 분리

엔진이 후보 점수, 다음 질문 ID, 결과 후보와 증거를 결정한다. 캐릭터 계층은 승인된 문안을 사용한다. LLM은 초기에 문안 제작 보조로 제한하는 방안을 제안한다. 실행 중 표현 생성은 별도 실험으로 두고, 도입 시 의미 검증과 기본 문안 대체를 요구한다.

## 후보 갱신

1. 데이터가 없는 시작점에서는 후보별 균등 가중치를 사용한다.
2. `logWeight = logPrior + Σ(reliability × logLikelihood)`로 순위를 갱신하는 기준선을 만든다.
3. `probably_*`는 전용 답변 분포를 사용해 단정 답변보다 약한 증거로 설계한다.
4. `unknown`은 점수를 갱신하지 않고 질문을 반복하지 않는다.
5. 같은 의미의 질문을 중복 증거로 쌓지 않는다. 동일 `correlationGroup`의 기여는 제한한다.
6. 정규화한 점수도 실제 정답 확률로 해석하지 않는다. 현실의 고민은 독립·단일 후보라는 가정을 만족하지 않는다.

## 다음 질문

현재 상위 후보를 구분할 예상 정보량에서 반복·민감도·질문 부담을 차감하는 규칙을 기준선으로 삼는다. 가중치는 실험 전 설정 파일에 고정한다. 이미 묻거나 조건을 만족하지 않는 질문은 제외한다. 계산상 정보량뿐 아니라 사용자가 질문을 이해하는지도 평가한다.

## 추측과 종료

- 초기 실험 가설: 질문은 최대 10개, 정답 추측은 최대 2회. 성능 약속이나 확정 제품 정책이 아니다.
- 내부 점수 차이, 서로 다른 근거 특징의 수, 모순 유무를 함께 확인해 추측한다.
- 점수 임계값은 아직 정하지 않는다. 검증 세트에서 잘못된 확신과 보류 비율을 비교해 설정한다.
- 사용자 응답은 `맞아요 / 일부만 맞아요 / 아니에요`로 구분한다. `일부`를 성공에 합산하지 않는다.
- 증거가 부족하거나 질문 예산을 소진하면 `insufficient_evidence`로 종료한다. 반드시 맞히도록 강제하지 않는다.
- 결과는 사용자가 제공한 증거 범위로 제한하고, 이름·사건·제삼자의 속마음을 만들어내지 않는다.

## 예외 처리

| 상황 | 처리 |
| --- | --- |
| 복합 고민 | 상위 후보 둘을 구분할 질문을 제시하고, 구분되지 않으면 복합 또는 보류로 표시 |
| 모순 답변 | 사용자를 탓하지 않고 맥락 차이 확인 또는 이전 답변 수정 제공; 수정 시 전체 점수 재계산 |
| 전부 모름 | 추측을 보류하고 정상 종료; 억지로 후보를 확정하지 않음 |
| 틀렸어요 | 해당 추측을 기록해 반복 방지; 다른 근거를 묻거나 추측 한도에서 종료 |
| 후보 밖 고민 | 낮은 증거 적합도·반복 거절을 신호로 보류; 정규화 최고 점수가 높다는 이유로 확정하지 않음 |
| 중도 종료 | 중단으로 기록; 정답 실패나 성공으로 바꾸지 않음 |

## 콜드스타트 평가

1. 후보별 포함·제외·경계 사례와 후보 밖·복합 사례를 사람이 작성한다.
2. 데이터 제작자와 독립 평가자가 사례를 나눠 검토하고, 유사 문장·상황이 양쪽에 섞이지 않도록 분리한다.
3. 합성 답변으로 점수 재현, 질문 중복 방지, 모순·모름·거절·종료 경로를 검증한다.
4. 개인정보를 강요하지 않는 별도 사용자 실험에서, 플레이 전 참가자가 스스로 적은 고민과 결과를 동의하에 비교한다. 원문을 서비스 기본 로그에 넣지 않는다.
5. `정확히 맞음 / 일부 일치 / 틀림 / 판단 어려움`과 구체성·설문처럼 느낀 정도를 별도로 수집한다.
6. 일반적인 위로만 제시한 기준선과 비교해, 추론이 추가 가치를 만드는지 확인한다.

측정: 전체 시작 대비 완료율, 완료 대비 명확한 일치율, 부분 일치율, 보류율, 오답 확신 사례, 질문 수 분포, 후보 밖 오판, 구체성 평가. 모두 분모·표본 수·후보 버전·질문 버전을 함께 보고한다. 합성 점수를 실제 고객 정확도로 보고하지 않는다.

## 다음 담당과 미해결 사항

- 제품팀·대표: 첫 후보 범위, 질문 예산, 사용자 검증 방식 확정.
- 캐릭터팀: 의미를 유지한 질문·보류·오답 인정 문안 작성.
- 개발팀: 위 계약을 타입으로 구체화하고 결정적인 엔진 기준선 구현.
- 품질팀: 독립 경계 사례와 의미 변형·후보 밖 오판 평가 준비.
- 미해결: 후보의 세분화 수준, 복합 후보 표현, 초기 분포의 타당성, 실제 사용자에게 유효한 종료 기준.
