# 제품개발팀 첫 기술 설계

상태: 코드 확인을 바탕으로 한 제안. 아래 게임·추론 엔진·서버는 아직 구현하지 않았다.

## 현재 확인한 구현

| 파일 | 확인한 동작 |
| --- | --- |
| `src/App.tsx` | 주제 선택과 질문 입력, 제출 후 고정 응답 표시; React 상태에만 유지 |
| `src/features/reading/demo.ts` | 네 주제별 고정 문구 반환; 질문 내용 분석 없음 |
| `package.json` | React·TypeScript·Vite·앱인토스 SDK 구성, lint와 웹/ait 빌드 명령 |

현재 화면은 이전 상담 데모다. 목표인 ‘고민을 설명하지 않아도 질문으로 짚는 게임’과 다르다. 로그인·서버 추론·게임 상태 머신이 구현되었다고 볼 근거는 없다.

## 제안 구조와 책임

| 계층 | 책임 | 소유 팀 |
| --- | --- | --- |
| 게임 UI | 시작, 질문과 답변 선택, 추측 확인, 정정·보류·종료 | 개발 |
| 세션 제어 | 이벤트 검증, 상태 전이, 버전 고정, 중복 입력 방지 | 개발 |
| 추론 엔진 | 점수 갱신, 다음 질문, 추측·보류 판단 | 추론 설계 / 개발 구현 |
| 후보·질문 데이터 | 포함·제외 사례, 의미, 답변 분포, 정책 버전 | 추론 |
| 표현 사전 | 의미를 보존하는 무당 대사, 보류·오답 문구 | 콘텐츠 |
| 서버 어댑터 | 이후 도입할 외부 AI·인증·영속화 경계 | 개발 |

첫 기준선은 승인 문안과 순수 함수 형태의 결정적 엔진을 제안한다. 런타임 생성형 AI 도입은 별도 검증 후 결정한다. API를 도입하면 비밀키를 서버에 두고 모델 실패가 게임 상태를 훼손하지 않도록 한다.

## 게임 상태 제안

`intro → asking → guessing → completed`를 기본으로 한다.

- `asking`: 유효한 질문에 답하면 엔진을 평가해 다음 질문·추측·보류로 이동.
- `guessing`: `맞아요`는 완료, `일부만 맞아요`와 `아니에요`는 확인 분기 또는 보류. 부분 일치를 정답으로 집계하지 않음.
- `reviewing`: 이전 답변을 수정한 뒤 수정 지점 이후 질문·추측을 무효화하고 유효한 답변으로 다시 계산. 분기 의존성 세부 규칙은 추론팀과 확정.
- `inconclusive`: 증거 부족·후보 밖·예산 소진으로 정상 종료. 정답 화면을 강제로 표시하지 않음.
- `error`: 복구 가능한 오류. 마지막 유효 상태를 보존하고 재시도·종료 제공.
- 모든 활성 상태에서 사용자가 중단 가능. 새 판은 기존 상태를 초기화.

이 명칭은 UI 상태 초안이다. 추론팀 `InferenceResult.status`와 동일한 enum으로 임의 확정하지 않는다.

## 데이터 계약 연결

기준 계약은 `docs/team-deliverables/inference-data.md`의 `Candidate`, `Question`, `Answer`, `Session`, `InferenceResult`다. 개발팀은 이를 복제해 별도 정본을 만들지 않고, 구현 착수 때 총괄·추론팀과 단일 TypeScript 계약을 확정한다.

추가 합의 항목:

- `InferenceResult.evidenceAnswerIds`가 참조할 안정적인 답변 ID 정의: 현재 `Answer` 초안에는 ID 필드가 없음.
- `Session.status`와 결과 `status`의 enum 및 상태 전이 매핑.
- 피드백의 `맞음 / 부분 / 틀림` 값, 추측 횟수와 거절 기록의 관계.
- `dataVersion`에 질문·후보·정책·문안 버전이 어떻게 연결되는지.
- 되돌리기로 무효화된 답변과 추측을 활성 추론에서 제외하는 규칙.
- 콘텐츠팀의 `건너뛰기`는 답변 enum에 없는 별도 UI 이벤트 제안이다. `unknown`이나 `no`로 자동 변환하지 않는다. 점수는 바꾸지 않고 질문 재노출·예산 계산을 어떻게 처리할지 추론팀과 확정한다.

UI는 현재 질문 ID·버전과 일치하는 입력만 받는다. 동일 화면의 빠른 연속 클릭은 한 이벤트로 처리한다. 원문 표현이 아니라 안정적인 ID로 계층을 연결한다.

## 저장과 측정

초기 플레이 상태는 메모리에 보관하는 방안을 제안한다. 새로고침 시 초기화됨을 제품 흐름에 반영하며, 복원 요구가 확정되면 저장 기간·삭제 정책을 함께 설계한다.

기본 이벤트 후보는 시작·답변 완료·추측 제시·사용자 평가·보류·중단이다. 이벤트에 답변 값, 질문 원문, 고민 후보 ID, 사용자 고민 원문을 기본 첨부하지 않는다. 질문 수·버전·익명 집계 등 최소 정보와 분모를 성장·품질팀과 합의한다. 운영 로그·오류 추적에도 민감한 payload를 남기지 않는다.

## 구현 순서와 검증

1. 제품 범위와 단일 데이터 계약 확정; 후보·질문 참조 무결성 검증.
2. 엔진 기준선 구현; 같은 입력의 재현성, 모름·모순·거절·예산 소진을 검증.
3. 세션 상태와 UI 연결; 처음부터 끝까지 플레이, 정정, 중복 클릭, 재시작 확인.
4. 승인 문안 연결; 질문 의미와 결과 근거가 변하지 않는지 콘텐츠·품질팀 검토.
5. lint/build 및 브라우저 모바일 크기 확인; 앱인토스 실제 환경 검증은 별도 수행.
6. 동의 기반 사용자 파일럿으로 구체성·몰입 검증; 합성 테스트 성과와 분리 보고.

## 다음 담당과 미해결 사항

총괄·추론팀은 계약의 답변 ID와 상태 enum을 확정한다. 제품팀은 첫 범주·질문 예산·복원 필요를 결정한다. 품질팀은 독립 경계 사례를 제공한다. 서버·런타임 AI·배포 방식은 이번 설립 작업에서 선택하지 않았다.
